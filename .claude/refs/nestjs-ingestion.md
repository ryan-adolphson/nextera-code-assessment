# Ingestion: unallocated turbines, CSV uploads, weather, rollups, demo data

- **Unallocated turbines (`@nextera/shared` `src/wind/unallocated.ts`):** an unknown turbine, or a `farm_id` that isn't the turbine's farm, is **held**, not rejected: `classifyReadings` → `holdReadings` (entry per (turbine_id, reported farm) in `unallocated_turbines`, reading in `held_telemetry`, 7-day retention) → 2xx. A **blocked** pair is dropped (2xx). A new pair beyond `MAX_PENDING_UNALLOCATED` (500, soft) gets 400 → DLQ. Lock order for every writer: `pg_advisory_xact_lock(hashtextextended('unallocated:'||turbine_id, 0))` in key order, then `FOR UPDATE` on the entry (a missing row can't be row-locked). `UNALLOCATED_CHANGED` `held` is published on entry creation or at most once per wall-clock minute, never for a redelivery. The API module `src/unallocated-turbines` (`@Roles('owner')`) resolves entries with `importHeld` (assign / keep / move; a move relies on the telemetry FK's `ON UPDATE CASCADE`), block and unblock. The composite FK still enforces turbine + farm on `telemetry`.
- **CSV upload (`POST /ingest/telemetry`, `CsvUploadController`):** for backfills, corrections and data from other systems.
  - **Request:** multipart field `file`, `telemetry.csv` format (`TELEMETRY_CSV_COLUMNS` from shared). Limit 10 MB / one file; larger returns 413.
  - **Parsing:** `parseTelemetryCsv()` (`telemetry-csv.ts`) validates every row with the same `IngestTelemetryDto` rules as Pub/Sub messages. It returns valid rows plus format errors by line; empty cells become "`<field>` is required". File-level problems (empty file, wrong header, wrong column count) throw.
  - **Storing:** `TelemetryIngestionService.ingestBatch()` merges format errors with the turbine/farm check (one `findMany` for the whole file).
    - **Any error:** 400 with `{ message, errorCount, errors: [{ line, errors }] }` (first 100), and **nothing is stored**.
    - **Otherwise:** one transaction of `createManyAndReturn({ skipDuplicates })` batches, then 201 `{ rows, inserted, duplicates, turbines }`. Re-uploads are idempotent; an empty `received_at` uses the upload time.
  - **Live updates:** publishes only the newest new reading **per turbine**, so a backfill doesn't flood dashboards. A Redis failure is logged, not thrown, because the data is already committed.
  - **Access in GCP:** the worker is private. Uploaders need `roles/run.invoker` (Terraform `ingestion_invokers`) and an identity token: `curl -H "Authorization: Bearer $(gcloud auth print-identity-token)" -F file=@x.csv <ingestion-url>/ingest/telemetry`.
- **Farm weather (`@nextera/shared` `src/weather`, table `farm_weather`):** 30-minute Open-Meteo buckets per farm (PK `(farm_id, time)` at :00/:30 UTC, FK farms CASCADE, `samples` 1–2, nullable metrics with 80 m wind, `fetched_at`; no source column). Only the forecast models' `minutely_15`: days before today − `HISTORICAL_LAG_DAYS` (5) from the Historical Forecast API (chunks ≤ 92 days), the rest from the Forecast API (both `start_date`/`end_date`, `timezone=UTC`, `wind_speed_unit=ms`); `fetchFarmWeather` retries 429/5xx/network/timeouts (3 attempts, 15 s) and validates the shape by hand; `toHalfHourBuckets` aggregates the 15-minute pairs (means; gust max; precipitation sum; vector-mean directions) and drops empty buckets; `upsertFarmWeather` always overwrites. Runner: `apps/ingestion/src/weather-sync` → `node dist/weather-sync/main.js [--from --to --farm…]` (default last 7 UTC days; `DATABASE_URL`, optional `OPEN_METEO_API_KEY` → `customer-*` hosts; pool `max: 2`, outside the services' connection budget; exit 1 if any farm failed); host: `npm run weather:sync`. A Cloud Run `--args` override must repeat `dist/weather-sync/main.js`. Read: `farmWeather` / `turbineWeather` in `queries.ts` → `GET /api/farms/:farmId/weather` and `GET /api/turbines/:id/weather` (`?from=&to=&interval=30min|daily&timeZone=`; viewer; daily = local days in `timeZone`, checked against `pg_timezone_names` and bound, aggregated in Postgres). Today's rows run to 23:30 UTC (forecast). Tests never call Open-Meteo (fixtures in `src/weather/__fixtures__`). Any e2e `TRUNCATE … farms` must include `farm_weather` and `farm_telemetry_rollups`.
- **Farm rollups (`@nextera/shared` `src/wind/farm-rollup.ts`, migration `20261101120000_farm_telemetry_rollups`):** `farm_telemetry_rollups` = 30-minute UTC buckets per farm (PK `(farm_id, bucket_start)`, FK farms CASCADE, `readings`, `turbines`, `<power|wind_speed|rotor_rpm|blade_pitch|gearbox_temp>_open|close|high|low`, `computed_at`) of the farm series (per timestamp: power **summed** over the turbines that reported, the rest **averaged**). `runFarmRollup(db, { mode, now })` is **one transaction**: `pg_try_advisory_xact_lock` (busy → `skipped`, exit 0), targets per farm = rows with `created_at > watermark − FARM_ROLLUP_LOOKBACK_MS` (10 min, for transactions still open; index `telemetry_created_at_idx`) by earliest `timestamp`, the consumed `farm_rollup_dirty` markers, and every farm's current UTC day (first run / `full`: every farm from the cutoff); per farm `DELETE` from its bucket then `INSERT … SELECT` from telemetry (so buckets a moved turbine left disappear); prune `< cutoff` (190 days before `min(now, newest reading)`, so the Jan 2026 fixture keeps its history); then the watermark (`farm_rollup_state` id 1 = the run's `clock_timestamp()`). A failed run changes nothing. **Moves:** the trigger `turbines_farm_rollup_dirty` (AFTER UPDATE OF farm_id, hand-written in the migration, invisible to `migrate diff`) inserts markers for the old and new farm from the turbine's first reading in the move's transaction, whoever moves it (API `move`, a seed, psql); no app code. Runner: `apps/ingestion/src/farm-rollup` → `node dist/farm-rollup/main.js [--full | --from YYYY-MM-DD] | [--every <s>]` (`DATABASE_URL`, pool `max: 2`; one run exits 1 on failure; `--every` logs failures and keeps looping, exits 0 on SIGTERM); host `npm run rollup` / `rollup:watch` (60 s). `db:seed`, `db:seed:demo` and `demo:reset` run one (`rollupAfterSeed`; `clearDemoReadings` also deletes the rollups, markers and watermark). Read: `farmDailyHistory` (`queries.ts`, ≤ `MAX_FARM_DAILY_RANGE_DAYS` 183 + 1 h DST slack, zone via `checkTimeZone`, days via `to_char(bucket_start AT TIME ZONE zone)`, open/close by `array_agg … ORDER BY bucket_start`) → `GET /api/farms/:farmId/telemetry/daily` (viewer; `ETag` = weak SHA-256 of the body (`common/etag.ts`), `Cache-Control: private, no-cache`, so the browser always revalidates and a new rollup shows at once; Express's `req.fresh` answers `If-None-Match` with 304; `fetch()` adds `Cache-Control: no-cache` to conditional requests, so e2e sends `max-age=0`) and MCP `get_farm_daily`. Timings (local, 200 turbines × 7 days = 403k rows): full ≈ 0.55 s, incremental ≈ 0.15–0.2 s, 183-day read ≈ 20 ms (8.8k rows).
- **Demo data and reset:** the fleet is `DEMO_TURBINES` (`src/seed/demo-fleet.ts`): 200 turbines, TURB001–TURB025 hand-placed and frozen (a spec pins them), TURB026–TURB200 from `demoFleetTurbines()` (per `DEMO_FARM_LAYOUT` farm total, 16–24, a contiguous id block on a staggered 3-decimal grid around the farm centre, ≥ 300 m apart; ids ending in 7 uncommissioned). Unknown demo ids stay outside it (TURB997–TURB999; the feed's unallocated one is TURB999→FARM01). The 20 stale turbines (10 %) live in `DEMO_ANOMALIES` (`generate-telemetry.ts`): `lagging` 8 × 20 min (yellow, incl. TURB011) + 6 × 45 min (orange, incl. TURB018), `stopped` 6 at 90–300 min (red, incl. TURB013 at 90); never a turbine with another anomaly or a `DEMO_UNALLOCATED` plan. `demoReportingLagMinutes(turbineId)` is the one rule the seed (`generateTelemetry` drops each turbine's last `lag` minutes) and the live feed (`demoFeedReadings` publishes at `floor(now) − lag`, skips `isDemoStopped`; 195 readings per tick) both follow. Lags must be multiples of 5. The seed generates 10 turbines at a time and stores 5,000-row transactions with `insertTelemetryBulk` (`src/wind/store-telemetry.ts`: rows that trigger an enabled rule via `insertTelemetryWithAlerts`, the rest via one `unnest` `INSERT … ON CONFLICT DO NOTHING`, ~4× faster than `createMany`, whose cost is per row in JS): 72 h ≈ 7 s (was 28 s), `demo:reset` 168 h (402,894 rows) ≈ 17 s of a ~40 s reset (was ~60 s for the seed alone). `npm run demo:reset` (`packages/shared/prisma/demo-reset.ts`, guards and the delete in `src/seed/demo-reset.ts`) refuses non-local hosts without `--allow-remote`, needs `--yes` without a TTY, deletes `telemetry_alerts`/`telemetry`/`held_telemetry`/`unallocated_turbines`/`farm_weather`/the farm rollups in one transaction (setup and moves stay), re-seeds 168 h, runs a farm rollup, runs `syncFarmWeather` in-process (warn on failure), then does a host `--once` tick and `DEMO_FEED_ENABLED=true docker compose up -d --no-deps --force-recreate --build demo-feed` (shell override, `.env` untouched; `--no-build`, `--no-weather`, `--no-feed` opt out). E2e: `packages/shared/test/demo-reset.e2e-spec.ts` (always `--no-weather --no-feed`).
