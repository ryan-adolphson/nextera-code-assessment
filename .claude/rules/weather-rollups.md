# Farm weather and rollups

- **Farm weather (Open-Meteo):** one 30-minute series per farm (farm coordinates; a turbine has none of its own and uses its current farm's) in `farm_weather`: PK `(farm_id, time)` (start of the 30-minute UTC bucket, :00/:30), FK `farms` CASCADE, `samples` (15-minute values in the bucket, 1–2), nullable `wind_speed_10m_ms`, `wind_speed_80m_ms`, `wind_direction_10m_deg`, `wind_direction_80m_deg`, `wind_gusts_10m_ms`, `temperature_2m_c`, `relative_humidity_2m_pct`, `surface_pressure_hpa`, `precipitation_mm`, `cloud_cover_pct`, `fetched_at`. Source: the forecast models' `minutely_15` only (native HRRR in North America, ICON-D2/AROME in Central Europe, interpolated hourly elsewhere): `syncFarmWeather` (`packages/shared/src/weather`) reads days older than `HISTORICAL_LAG_DAYS` (5) from the Historical Forecast API (`historical-forecast-api.open-meteo.com/v1/forecast`, from ~2022; chunks ≤ 92 days) and recent days from the Forecast API (`start_date`/`end_date`, `timezone=UTC`, `wind_speed_unit=ms`; retries 429/5xx/timeouts 3×, 15 s timeout, requests one at a time). `toHalfHourBuckets` aggregates each :00+:15 / :30+:45 pair (speeds, temperature, humidity, pressure, cloud: mean; gusts: max; precipitation: sum; directions: vector mean), drops buckets without any value, and `upsertFarmWeather` overwrites (the newer fetch wins; no archive/ERA5). Today's rows run to 23:30 UTC (forecast), so "latest" means the newest bucket that has started. One farm failing doesn't stop the others; the runner exits 1 if any failed. Daily figures are never stored: `farmWeather` / `turbineWeather` (`queries.ts`, `interval=daily`) aggregate per local day in `timeZone` (IANA, default `UTC`, checked against `pg_timezone_names`, bound never interpolated; unknown → 400) in Postgres (wind means/maxes, gust max, vector-mean 80 m direction, temperature min/max/mean, precipitation sum, `samples` = buckets: 48, 46/50 on a DST day); `30min` returns the buckets (UTC times; `timeZone` only echoed). Both endpoints return `{ farmId, [turbineId], from, to, interval, timeZone, points }`; `turbineWeather` 404s an unknown turbine. The runner uses its own pool (`createPrismaClient`, `max: 2`). Tests never call Open-Meteo (injected `fetch`, recorded fixtures in `src/weather/__fixtures__`). **Licence:** the free API is non-commercial only (~10k calls/day); production use needs a paid key, `OPEN_METEO_API_KEY` (switches to the `customer-*` hosts, incl. `customer-historical-forecast-api`; never logged). Every e2e `TRUNCATE` of `farms` must list `farm_weather` too. MCP: `get_weather`.
- **Farm rollups (History tab):** `farm_telemetry_rollups` (PK `(farm_id, bucket_start)`, FK farms CASCADE): 30-minute UTC buckets of each farm's series (per measurement timestamp: power **summed** over the turbines that reported, wind/rotor/pitch/gearbox **averaged**), with `readings`, `turbines` (distinct reporters) and `<power|wind_speed|rotor_rpm|blade_pitch|gearbox_temp>_open|close|high|low`, `computed_at`. Derived data, written only by the farm rollup job (`runFarmRollup`, `@nextera/shared` `src/wind/farm-rollup.ts`), never on ingest. Each run is one transaction with an advisory lock (a concurrent run is skipped) and recomputes, per farm, from the earliest bucket touched by telemetry rows created since the watermark (`farm_rollup_state`, on `telemetry.created_at`, index `telemetry_created_at_idx`, 10-minute lookback), from any `farm_rollup_dirty` markers, and over the current UTC day; it prunes buckets older than 190 days before the newest reading. A failed run changes nothing, the watermark included. A move rewrites `telemetry.farm_id` without new rows, so the trigger `turbines_farm_rollup_dirty` (AFTER UPDATE OF farm_id, in the migration; Prisma doesn't model it) writes markers for both farms from the turbine's first reading in the move's transaction. After a committed, non-skipped run the job publishes `farm-rollup.completed` (`FARM_ROLLUP_COMPLETED`, `{ asOf }` = the run's watermark; global, no farm ids) through `EventStore.publish`, so open History tabs reload. Best effort: a Redis failure is logged and the run still exits 0. `REDIS_URL` is optional for this job (without it nothing is published, and that is logged), because `deploy.yml` updates the job image independently of `terraform apply`. `db:seed`, `db:seed:demo` and `demo:reset` call `runFarmRollup` directly and publish nothing. Daily candles are aggregated on read in any time zone (`farmDailyHistory`; open = first bucket's open, close = last bucket's close, high/low = max/min, `turbines` = max). `GET /api/farms/:farmId/telemetry/daily` sends a weak ETag over the body (304 on `If-None-Match`) and `Cache-Control: private, no-cache` (the browser revalidates every request, so a new rollup run shows at once; the web keeps its own 15-minute cache, which Refresh/Retry and `farm-rollup.completed` bypass); ≤ 183 days (+1 h DST slack). `db:seed`, `db:seed:demo` and `demo:reset` run one rollup after seeding; after CSV uploads in browser tests run `npm run rollup` (or wait for the compose `farm-rollup` service). Any e2e `TRUNCATE … farms` must include `farm_telemetry_rollups`. Its incremental scan and per-farm recompute prune to the partitions of their time range. Recomputing every farm's current day every 15 minutes is the cost to watch at 10,000 farms.
