# Backend conventions

- **Data model:** `farms` → `turbines` → `telemetry`. `turbines`: UUID `id` (internal, never exposed by the API), business key `turbine_id` ('TURB001', unique; used by payloads, CSVs, API ids, SSE and URLs), `commissioned` (default false). `telemetry`: UUID id; composite FK `(turbine_id, farm_id)` → `turbines(turbine_id, farm_id)`; unique `(turbine_id, timestamp)`. `created_at` (default now(), set by Postgres) is the real insert time; `received_at` can come from the payload/CSV for backfills; neither `created_at` nor the internal ids are in API responses. "Latest" and trends use the measurement `timestamp`, never `received_at` or `created_at`. Aggregates such as `/telemetry/stats` are computed in Postgres over exactly the rows the matching list endpoint returns. `alerts_config` holds alert thresholds: `measurement_metric` (enum of the telemetry metric columns), `comparison` (`above`/`below`), `value_metric`, `alert_level` (`info`/`warn`/`error`), `enabled` (default true; disabled rules are kept but not evaluated); one rule per (metric, comparison, level). `telemetry_alerts` (PK `(telemetry_id, alert_id)`): the rules each reading triggered, a join table (not an array column) so both ids are real FKs; `telemetry_id` CASCADE, `alert_id` RESTRICT (Postgres 23001, Prisma P2003): `DELETE /api/alert-configs/:id` of a rule that readings triggered returns 409, disable it instead (`PATCH {enabled: false}`). Ingestion (Pub/Sub and CSV) evaluates the enabled rules in the insert's transaction with `triggeredAlerts` (`@nextera/shared`, strict `>`/`<`); reads `include: TELEMETRY_ALERTS_INCLUDE`, and `TelemetryResponse.alerts` (API + SSE) is the joined rules as they are now (no snapshot), worst level first. No backfill: older readings have none. `users`: UUID `id` (the JWT `sub`), unique normalised (trimmed, lower-case) `email`, `password_hash` (argon2id), `role` (enum `role`: `viewer`/`owner`/`admin`), `active` (default true), `created_at`, `updated_at`; rows come only from `npm run db:seed` (or `db:seed:demo`). `unallocated_turbines`: UUID `id` (exposed: the API's actions need it), `turbine_id`, `reported_farm_id` (no FK: the farm may not exist), `kind` (`unknown_turbine`/`farm_mismatch`; the API derives it live), `status` (`pending`/`blocked`), `first_seen_at`/`last_seen_at` (server receive times), `blocked_at`, `blocked_by` (→ `users`, SET NULL); unique `(turbine_id, reported_farm_id)`. `held_telemetry`: readings waiting for a decision (the telemetry columns + `unallocated_id`, CASCADE), unique `(unallocated_id, timestamp)`. Unblock deletes the entry (the pair's next reading starts a new one). UUID ids are generated by Postgres (`gen_random_uuid()`).
- **Ingestion:** payload fields and CSV uploads both use the `telemetry.csv` format. Each new reading's triggered enabled rules are stored in `telemetry_alerts` in the same transaction. CSV uploads are all-or-nothing for format errors: every error is reported by line and nothing is stored if any row is invalid. Duplicates are skipped and counted. Idempotent on `(turbine_id, timestamp)`. Anomalous readings are stored. Invalid payloads return 400 (→ DLQ after retries). **Unallocated turbines:** readings for an unknown turbine or with a farm mismatch are **held** (2xx), not rejected: `classifyReadings` / `holdReadings` (`@nextera/shared`, `src/wind/unallocated.ts`) upsert an `unallocated_turbines` entry per (turbine_id, reported farm) and store the reading in `held_telemetry` (kept 7 days, `HELD_RETENTION_MS`). Readings for a **blocked** pair are dropped (2xx). At most `MAX_PENDING_UNALLOCATED` (500) pending entries: a new pair beyond that gets 400 (→ DLQ). CSV results add `held` and `blocked` counts. Writers take a per-turbine advisory lock, then `FOR UPDATE` on the entry, so a reading never races an assign. Owners resolve entries in the web app (assign / keep / move / block); `importHeld` moves held readings into `telemetry` with alerts evaluated. A move updates `turbines.farm_id`, and `telemetry.farm_id` follows through the FK's `ON UPDATE CASCADE` (the turbine's whole history moves). Events after commit: `unallocated-turbine.changed` (`UNALLOCATED_CHANGED`, `{action, id, turbineId}`), plus `fleet.changed` (`FLEET_CHANGED`, `{turbineId}`) and `telemetry.received` (newest imported reading) after assign/keep/move. SSE goes to every signed-in user, so these payloads carry only ids and actions. **Group commit:** Pub/Sub readings go through `TelemetryBatcher` (`apps/ingestion/src/ingestion/telemetry-batcher.ts`), with no timer. An idle worker flushes a reading at once. While a flush runs, others queue (at most `INGEST_MAX_QUEUED`, default 500), and the next flush writes up to `INGEST_BATCH_MAX` (default 100) in one transaction. The result is per reading: a repeat in the batch or an existing row is `duplicate`, and the first occurrence wins. After commit: one `telemetry.received` per stored reading through `EventStore.publishLive` (pipelined PUBLISH to `turbineChannel(id)`, no stream), then the held events. A Redis failure is logged and the reading is still acked. A failed batch transaction is retried one reading at a time through the single-reading transaction, so a bad reading (a new pair over the cap → 400) fails alone. A full queue gives an immediate 503 + `Retry-After` (`QueueFullFilter`) and writes nothing, so Pub/Sub retries. On SIGTERM the batcher drains the queue (8 s), then rejects the rest with 503. CSV uploads still use `ingestBatch`.
- **Farms cache:** `FarmsCacheService` (`apps/api/src/farms-cache`) serves `GET /api/farms` (`get(load)`), `GET /api/farm-summaries` and `GET /api/fleet/summary` (`getKeyed(key, load)`); `invalidate()` clears every key: serialized JSON bytes plus an ETag, single-flight, per instance, TTL `FARMS_CACHE_TTL_MS` (default 5000, 0 = off), with a generation counter so a load started before an invalidation is never stored. Anything in the API that changes the farms response must call `farmsCache.invalidate()` after the commit and before publishing. Today: setCommissioned, unallocated assign/keep/move, alert-config writes, and `EventsService` on `fleet.changed` and `fleet.tick` from Redis, before the event reaches SSE. Ingestion telemetry is covered by the TTL only. e2e tests that write through Prisma directly must call `FarmsCacheService.invalidate()` before reading `/api/farms`. Don't return a Buffer from a Nest handler: use `@Res()` and `res.send`.
- **Partitions and derived tables:** `telemetry` and `telemetry_alerts` are daily range partitions (on `timestamp` / `reading_timestamp`) plus DEFAULT partitions (`telemetry_default`, `telemetry_alerts_default`); Prisma sees one table. `telemetry` PK is `(id, timestamp)` (address a reading with `id_timestamp`); `telemetry_alerts` PK is `(telemetry_id, alert_id, reading_timestamp)`, with a composite FK. Joins from `telemetry_alerts` to `telemetry` must carry `reading_timestamp`, and time-range queries must prune. Partitions are created and dropped only by the partition-maintenance job and the SQL functions `telemetry_ensure_partition` / `telemetry_drop_partitions_before`; creating a day moves its DEFAULT rows with their alerts. `TELEMETRY_RETENTION_DAYS` (unset = keep everything; 31 on GCP) drops whole days with their alerts and purges older DEFAULT rows. Overlapping maintenance runs skip (advisory lock). `turbine_latest` (PK `turbine_id`, composite FK to turbines, so a move carries `farm_id`) is upserted in the reading's transaction by `insertTelemetryWithAlerts` / `insertTelemetryBulk`, only when newer, sorted by turbine; any new writer of `telemetry` must use them or call `refreshTurbineLatest`. `farm_live_summary` is rebuilt every minute by the live-summary job, which then publishes `fleet.tick` `{asOf}`. Ingestion caches the enabled alert rules for `ALERT_RULES_CACHE_TTL_MS` (30 s), so a rule edit may take that long to apply to new readings. e2e truncates of `turbines` or `farms` must also list `turbine_latest, farm_live_summary, anomaly_episodes`.
- **Scale reads:** `GET /api/turbines` (`listTurbines`, `wind/fleet-queries.ts`) is keyset-paged over `turbines` ⨝ `turbine_latest` (`sort=id|farm|commissioned|time|power|wind|gearbox`, `dir`, `limit` ≤ 100). A cursor is a position (sort, dir, key, id); no reading sorts last in both directions; `power|wind|gearbox` need `farmId` (400). `q` is a case-insensitive trigram substring of the turbine id or a farm id/name (≤ 50 farms). `total` is exact from `farm_live_summary` when only `farmId`/`commissioned` filter (can lag a minute), else counted to 10,000 (`totalCapped`). `/api/farm-summaries` and `/api/fleet/summary` read `farm_live_summary` (farms it hasn't summarised are computed on the spot). `/api/farms/:id/turbine-markers` ≤ 2,000. `GET /api/alerts` is `{ items, nextCursor }`, newest first, default 500, max 1000. `/api/reports/telemetry` refuses more than `MAX_REPORT_ROWS` (100,000) with 400 before loading. `GET /api/farms` is deprecated: 413 above 5,000 turbines. A segment read in id order must bound `turbine_latest` in the `LEFT JOIN … ON` too, or the planner merge-joins it from the start.
- **Live events:** readings are live only: `EventStore.publishLive` PUBLISHes `{type, data}` to `turbineChannel(id)` (`telemetry:<id>`), with no XADD. The stream holds low-volume events only. `GET /api/events?turbines=a,b,c` (optional, ≤ 100 business ids, deduped; bad or empty entries → 400) carries all global events plus the listed turbines' `telemetry.received`, never replayed, sent with `id` = the connection's last global id (empty before any). Don't send an SSE message without an `id`: Nest invents a counter id that overwrites `Last-Event-ID`. `EventsService` reference-counts per-turbine subscriptions on one subscriber connection, releasing in the Observable teardown. Each connection buffers at most `MAX_BUFFERED_READINGS` (200) readings, drop-oldest, flushed on socket `drain`: Nest's SSE writer queues without bound, so this is the only bound. A query DTO on `/api/events` must declare `access_token`, or the global whitelist 400s the query-token flow.
- **API:** DTO validation and Prisma error mapping. CORS is limited to `CORS_ORIGINS` (`http://localhost:4200` locally, plus the compose `web` origin for the compose `api`; in GCP Terraform sets `https://nextera-web-<project number>.<region>.run.app` + `web_domain`. The hashed run.app URL is not allowed: use the `web_url` output). Every route needs a signed-in user unless it is `@Public()` (see **Auth**); each `/api/alert-configs` write publishes `alert-config.changed` (`ALERT_CONFIG_CHANGED` in `@nextera/shared`) after the commit.
- **MCP server (`apps/mcp`):** local stdio only (started by the MCP client from `.mcp.json` / Claude Desktop), never deployed. **Read-only, and it stays that way:** tools only read through the shared queries, and every pooled connection sets `-c default_transaction_read_only=on`, so any write fails in Postgres with SQLSTATE 25006; never add a tool that writes, and never drop that setting. In GCP, point `MCP_DATABASE_URL` at a role that has only `SELECT`. stdout carries only JSON-RPC: log to stderr. It reads `MCP_DATABASE_URL`, else `DATABASE_URL` (repo-root `.env`), pool `max: 2`. Tool arguments mirror the API's limits (`limit` ≤ 2016, ranges ≤ 31 days, timestamps via `timestampProblem`), and errors (unknown turbine, bad range, database failure) are `isError` results, never a crash. `get_farm_daily` reads `farmDailyHistory` (daily candles of a farm, ≤ 183 days, `timeZone`). `get_weather` reads `farmWeather` / `turbineWeather` (exactly one of `farmId` and `turbineId`, a Zod refinement through `defineTool`'s `refine`; a turbine gets its farm's weather; `daily` by default, local days in `timeZone` (default UTC), or `30min`; ≤ 31 days). `list_unallocated` (pending|blocked, optional `turbineId`) and `get_unallocated_readings` (entry UUID, `limit` ≤ 2016) read `listUnallocated`/`getUnallocated`/`heldReadings` but never show `blockedBy` (the API shows that email to owners only; MCP has no users). `get_turbine` lists a turbine's pending unallocated entries and points an unknown but reporting id to `list_unallocated`.
- **Anomalies:** `GET /api/anomalies?from=&to=` (viewer) and the MCP `list_anomalies` (newest 100 episodes; `totalEpisodes` and `estimatedLostKwh` cover all) read stored episodes through `anomaliesInRange` (`wind/fleet-queries.ts`; ≤ 31 days, ≤ 5,000 episodes, then `truncated`). The hourly anomaly-rollup job writes `anomaly_episodes` and `anomaly_expected_power` with `anomalyEpisodesSql` (`wind/anomaly-sql.ts`, rules and constants in `wind/anomalies.ts`); `listAnomalies` (on read) remains as the oracle for tests. Episodes are stored whole: crossing episodes are clipped on the 5-minute grid, lost kWh pro rata. They appear up to an hour late, expected power is the rollup's last 24 h (a turbine sample at scale), and a reading more than 120 min late isn't seen. The rules: "Consecutive" means no gap > 5 min in the turbine's readings (gaps-and-islands with window functions). `low_power_in_wind`: ≥ `ANOMALY_MIN_READINGS` (3) readings with wind ≥ 10 m/s and power < 0.1 × the fleet median power in the same 1 m/s wind bin within the range (a bin with < 20 readings falls back to the nearest populated bin below; with none, < 100 kW counts as low and there is no estimate); `estimatedLostKwh` = Σ max(0, expected − actual) × 5/60 (a fleet-derived estimate, not a power curve). `stuck_sensor`: the same gearbox, wind or rotor rpm value for ≥ `STUCK_SENSOR_MIN_READINGS` (12, 1 hour) consecutive readings while the turbine's power range over them is ≥ `STUCK_SENSOR_MIN_POWER_RANGE_KW` (50 kW, calibrated on generated data: plateaus ≤ 12.7 kW, the seeded fault 467 kW); flat power too means a plateau or a stopped turbine, not a sensor fault; power itself is never "stuck". Stopped turbines are not anomalies (staleness pills cover them). The `bins` CTE must stay `MATERIALIZED` and the readings CTE `NOT MATERIALIZED` (see the SQL comments). Demo data: 168 h gives exactly the two seeded faults, 0 false positives, 21,000 kWh, about 1.9 s.
